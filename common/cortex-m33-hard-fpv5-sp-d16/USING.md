# Using the lib-build artifacts — cortex-m33-hard-fpv5-sp-d16

Generated by lib-build for target **`arm-none-eabi`** with flags
`--target=arm-none-eabi -mcpu=cortex-m33 -mfloat-abi=hard -mfpu=fpv5-sp-d16`.

All paths below are relative to this SDK root:

```text
E:/lib-build/out/arm-none-eabi/cortex-m33-hard-fpv5-sp-d16
```

The `examples/` directory next to this file contains a starter CMake
template that demonstrates the minimum runtime contract described here.
Copy it, edit `memory.ld` + `startup.c`, then adapt the board I/O,
time source and threading hooks for your firmware.

---

## 1. What files do I take?

### Must include

| Path | Purpose |
|---|---|
| `include/c++/v1/` | libc++ headers (`<vector>`, `<mutex>`, ...) |
| `include/c++/v1/__external_threading` | libc++ threading contract (templated) |
| `picolibc/include/` | picolibc C headers (`<stdio.h>`, `<time.h>`, ...) |
| `lib/libc++.a` | C++ standard library |
| `lib/libc++abi.a` | C++ ABI support (`typeinfo`, `__cxa_pure_virtual`) |
| `lib/baremetal/libclang_rt.builtins-arm.a` | compiler intrinsics (`__aeabi_*`, 64-bit divmod, soft-float helpers...) |
| `picolibc/lib/libc.a` | C standard library |
| `picolibc/lib/libm.a` | math library |
| `picolibc/lib/crt0.o` | C runtime startup (zeroes bss, copies data, runs C++ ctors, calls main) |
| `picolibc/lib/picolibcpp.ld` | reference linker script (you can include or copy) |

### Do not need

- `lib/libc++experimental.a` — only needed if you use experimental libc++ TS features
- `picolibc/lib/libg.a`, `libnosys.a` — empty stubs kept for GNU `-lg -lnosys` compatibility
- `picolibc/lib/libdummyhost.a` — picolibc's internal test harness
- `picolibc/lib/crt0-hosted*.o`, `crt0-semihost*.o` — only for QEMU / debuggers that emulate a host
- `picolibc/lib/picolibc_linux.ld`, `picolibcpp_linux.ld` — Linux user-space layouts

## 2. `--sysroot` vs `-isystem`, and why both

`--sysroot=<dir>` tells clang "treat this as the filesystem root for
library and header search". It does **not** require a real Unix layout
on your host — clang just prepends it to its own built-in `/include` and
`/lib` search paths. Our `picolibc/` directory is a perfectly valid
sysroot because it has the canonical `include/` + `lib/` pair inside.

libc++, libc++abi and compiler-rt are **not part of the sysroot** — they
live next to it — so you pass their header directory with `-isystem` and
their library directory with `-L`.

```text
E:/lib-build/out/arm-none-eabi/cortex-m33-hard-fpv5-sp-d16/
├── include/c++/v1/                      ← -isystem ... (libc++ headers)
├── lib/                                 ← -L ...        (libc++ / libc++abi)
├── lib/baremetal/                       ← -L ...        (compiler-rt builtins)
└── picolibc/                            ← --sysroot=... (picolibc C library)
    ├── include/
    └── lib/
```

## 3. Minimal clang command line

```bash
clang++ \
    --target=arm-none-eabi -mcpu=cortex-m33 -mfloat-abi=hard -mfpu=fpv5-sp-d16 \
    \
    `# Search paths` \
    --sysroot=E:/lib-build/out/arm-none-eabi/cortex-m33-hard-fpv5-sp-d16/picolibc \
    -isystem E:/lib-build/out/arm-none-eabi/cortex-m33-hard-fpv5-sp-d16/include/c++/v1 \
    -L E:/lib-build/out/arm-none-eabi/cortex-m33-hard-fpv5-sp-d16/lib \
    -L E:/lib-build/out/arm-none-eabi/cortex-m33-hard-fpv5-sp-d16/lib/baremetal \
    \
    `# User-code flags: no host STL, no exceptions / RTTI` \
    -nostdinc++ \
    -nostdlib++ \
    -ffreestanding \
    -fno-exceptions \
    -fno-rtti \
    \
    `# Linker: picolibc crt0.o is the runtime entry point` \
    -T memory.ld \
    E:/lib-build/out/arm-none-eabi/cortex-m33-hard-fpv5-sp-d16/picolibc/lib/crt0.o \
    \
    main.cpp startup.c syscalls.c libcpp_threads.c \
    \
    `# Libraries must be in this order:` \
    -lc++ -lc++abi \
    -lc -lm \
    -lclang_rt.builtins-arm \
    \
    -o firmware.elf
```

CMake equivalent is in `examples/CMakeLists.txt` + `examples/toolchain.cmake`.

## 4. Startup chain and what `startup.c` has to provide

The expected Cortex-M startup path is:

`Reset_Handler -> SystemInit() -> _start -> main()`

`Reset_Handler` comes from your startup file and calls chip-level early init.
`_start` comes from picolibc `crt0.o`, which then handles `.bss` zeroing,
`.data` copy, TLS image setup, C++ global-ctor dispatch, and finally calls
`main`.

This flow does **not** assume any RTOS-specific user-main trampoline such as
`entry()` or `RT_USING_USER_MAIN`; if your firmware wants an RTOS-managed main
thread, that is an additional adaptation layer on top of this startup chain.

Your startup file still has to provide:

1. The Cortex-M interrupt vector table.
2. Setting `MSP` (comes from vector table entry 0).
3. Enabling the FPU (if hard-float).
4. Any chip-specific clock / PLL init.

The template `examples/src/startup.c` provides the minimum Cortex-M pieces.
You still need to edit it to append your chip's peripheral IRQ handlers to
`g_pfnVectors[]`.

### Symbols the linker script MUST export

| Symbol | Used for |
|---|---|
| `__stack` | initial MSP (vector table slot 0) |
| `__text_end` / `__etext` | end of code in flash |
| `__preinit_array_start/_end`, `__init_array_start/_end`, `__fini_array_start/_end` | C++ ctor/dtor arrays |
| `__data_start`, `__data_end`, `__data_source`, `__data_size` | `.data` VMA + LMA + length |
| `__bss_start`, `__bss_end`, `__bss_size` | `.bss` zero-fill range |
| `__tls_base`, `__tdata_start/_end/_source/_size`, `__tbss_start/_end/_size`, `__tls_size`, `__arm32_tls_tcb_offset` | TLS image setup used by picolibc / libc++ runtime |
| `_end` / `end` | heap origin (used by `_sbrk`) |
| `__heap_end` | heap upper bound |

All of these are already wired up in `examples/memory.ld`; if you write
your own linker script, use that as a reference.

### TLS note

Keeping `.tdata` / `.tbss` and the TLS linker symbols is necessary, but it is
not sufficient for a multithreaded system. picolibc provides the runtime pieces
that know how to initialise a TLS image, but your firmware / RTOS still has to
provide:

- per-thread TLS block allocation
- TLS context switch / active-thread selection
- TLS destructor handling for thread exit paths

In other words: the linker script and `crt0.o` make TLS *possible*; your
threading adaptation makes TLS *work per thread*.

### Sections the linker script MUST `KEEP`

Any section that only contains pointers — in particular
`.isr_vector`, `.preinit_array`, `.init_array`, `.fini_array` — will be
dropped by `--gc-sections` unless the linker script wraps them in
`KEEP(*(...))`. A "my program compiles but global ctors never run" bug
is almost always a missing `KEEP` on `.init_array`.

## 5. What `syscalls.c` has to provide (picolibc POSIX hooks)

picolibc was built with `-Dposix-console=true`, so its stdio forwards
to these symbols:

- `ssize_t write(int fd, const void*, size_t)` — `printf` ends up here
- `ssize_t read(int fd, void*, size_t)` — `scanf` / `fgetc` ends up here
- `int close(int)`, `int fstat(int, struct stat*)`, `int isatty(int)`,
  `off_t lseek(int, off_t, int)` — POSIX mandate but rarely used on baremetal
- `void* sbrk(ptrdiff_t)` — backs `malloc`

In addition libc++ `std::chrono::steady_clock` calls through to:

- `int clock_gettime(clockid_t, struct timespec*)` — wire to your monotonic
  hardware / RTOS time source

`examples/src/syscalls.c` provides a starter implementation of all of the above.
It uses weak `board_putc` / `board_getc` hooks as one possible board I/O path,
but those hooks are just example integration points, not an ABI requirement.

## 6. What `libcpp_threads.c` has to provide

libc++ was built with `LIBCXX_HAS_EXTERNAL_THREAD_API=ON`, which means
any use of `std::mutex`, `std::thread`, `std::condition_variable` or
`std::call_once` in your code pulls in symbols called `__libcpp_*`.
There are ~25 of them, **but the linker only asks for the ones your
code actually uses**.

The full contract is documented in:

```text
E:/lib-build/out/arm-none-eabi/cortex-m33-hard-fpv5-sp-d16/include/c++/v1/__external_threading
```

`examples/src/libcpp_threads.c` is a minimal placeholder that can satisfy the
linker for simple firmware, but it is not a complete threading port. For a real
RTOS-backed system you must replace the bodies with your own implementation of
the `__external_threading` contract, including mutexes, condition variables,
thread lifecycle, and any TLS support your code paths require.

If your code or libraries use `thread_local`, `errno`, `std::promise`,
`std::async`, or any other per-thread state, you must also provide working TLS
glue below `__libcpp_tls_*`; the placeholder implementation is not enough.

Typical RTOS mappings look like:

| Your API | Replace with |
|---|---|
| `__libcpp_mutex_lock/unlock/...` | FreeRTOS `xSemaphoreTake/Give`, Zephyr `k_mutex_lock`, CMSIS-RTOS2 `osMutexAcquire` |
| `__libcpp_thread_create/join/...` | RTOS task create / join |
| `__libcpp_thread_yield` | `taskYIELD()` / `k_yield()` / `osThreadYield()` |
| `__libcpp_thread_sleep_for_ns` | `vTaskDelay(ns_to_ticks(n))` / `k_sleep(K_NSEC(n))` / `osDelay(...)` |
| `__libcpp_condvar_*` | optional; only needed for `std::condition_variable` |

## 7. Memory map template

Replace the `MEMORY { flash, ram }` block in `examples/memory.ld` with
your chip's actual map. The rest of the script — every `SECTION`
definition, every symbol listed above — is already correct for Cortex-M
+ picolibc + libc++.

```
FLASH                           RAM
┌─────────────────────┐         ┌─────────────────────┐
│ .isr_vector         │         │ .data (VMA)         │
│ .text               │   ┌──→  │ .tdata + .tbss      │
│ .rodata             │   │     │ .bss                │
│ .init_array         │   │     │ heap →              │
│ .fini_array         │   │     │     ↑               │
│ .data  (LMA) ───────┼───┘     │     free RAM        │
│ .tdata (LMA) ───────┼──────→  │     ↓               │
└─────────────────────┘         │ ← stack (MSP)       │
                                └─────────────────────┘
```

## 9. Verifying the result

After `cmake --build build` you should have `build/firmware.elf`. Quick
sanity checks:

```bash
# Every required crt0 symbol must be resolvable in the final ELF.
llvm-nm firmware.elf | grep -E '__(stack|data_start|data_source|bss_start|tls_base|tdata_start|init_array_start|fini_array_start)'

# Memory usage.
llvm-size firmware.elf

# Confirm architecture + FPU attributes match cortex-m33-hard-fpv5-sp-d16.
llvm-readelf --arch-specific firmware.elf | grep -E 'CPU_name|CPU_arch|FP_arch|ABI_VFP_args'
```

If any of the `__…_start` symbols above prints with address `0` or is
missing, your linker script is dropping a section — revisit the KEEP
directives.
